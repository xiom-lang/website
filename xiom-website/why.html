Purpose

Specification and implementation are the same artifact.

Why XIOM exists: closing the gap between what a programmer intends and what the compiler can verify.

The problem

Most code is no longer written by a single engineer who holds the entire system in their head. It is written by teams, maintained by people who did not write it, and increasingly generated by AI tools. Yet the dominant systems languages were designed for a world where a human expert reads every line before it runs.

The contract between the programmer and the compiler has not changed since 1972. The consequences are visible everywhere:

  • Memory bugs that exist because the language cannot express intent clearly enough for the compiler to catch
  • AI-generated code that compiles and passes tests but violates assumptions nobody wrote down
  • Interfaces documented in comments that no toolchain enforces
  • Languages so complex that even experts cannot reason about every corner case

The idea

XIOM puts the specification inside the function signature, where the compiler can read it. A function that requires its input to be non-zero says so. A function that guarantees its output is sorted says so. A type that must never hold a negative value says so.

These are contracts the compiler enforces: today through runtime guards with precise error messages, and later through static proof.

Why AI changes the game

Code review cannot be the only safety layer when the volume of generated code exceeds what humans can read. Contracts make output verifiable by construction: the author states intent, the compiler checks the implementation against it, and violations surface at compile time or the first test run -- not in production.

The three pillars

Safe

No garbage collector. No null. No hidden allocations. Ownership with lexical scope borrowing -- simpler than Rust, same safety guarantee.

Verified

Contracts are part of the language, not the documentation. The compiler is the verifier: runtime guards today, static proof later.

Precise

One way to write each thing. No implicit behaviour. What you read is what runs. derive handles the boilerplate.

What XIOM is not

  • Not a research language -- it is meant for production use.
  • Not a domain-specific language -- graphics, networking, and AI are libraries, not built-ins.
  • Not a scripting replacement -- it competes with Rust, Zig, and C++.
  • Not finished -- this page describes intent; the language is being built.
